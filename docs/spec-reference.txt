

DevPulse
Developer Specification  —  v0.1
Windows Tray Notifier • Rule-Based Inboxes • Kanban Board
Target Platform: .NET 8 on Windows




Table of Contents



1. Purpose
DevPulse is a lightweight Windows tray application that monitors Azure DevOps pull request activity, classifies events into user-defined inboxes, and surfaces a Kanban board view of work items — all without requiring a browser to be open.

The application shall:
Poll Azure DevOps on a configurable interval for both PR events and work items
Normalize author identities before rule evaluation to handle inconsistent ADO identity formats
Classify PR events into inboxes using expressive include/exclude rules with keyword packs
Maintain a system “Needs My Attention” inbox above all user-defined inboxes
Surface selected inboxes as Windows toast notifications with per-inbox unread counts in the tray menu
Support PR mute and snooze to suppress noise for specific PRs or authors
Collapse repeated bot or system events into grouped inbox rows
Display a Kanban board with aging indicators and quick-toggle view filters
Provide a debug/audit window and a rule test mode to aid configuration

This is a personal productivity tool. It is read-only toward Azure DevOps in v0.1.

2. Goals
2.1 Primary Goals
Surface the right PR activity at the right time, with minimal noise
Make the “Needs My Attention” inbox the single interruptive signal for reviewers
Provide a board that shows work item age and staleness, not just state
Make inbox rules easy to configure, test, and debug without code changes

2.2 Secondary Goals
Persist local state so duplicate notifications are never shown after restart
Keep the app lightweight and easy to deploy as a single self-contained executable
Support simple JSON-based config export/import

2.3 Non-Goals
Posting comments or editing PRs or work items from the app
Full replacement of the Azure DevOps UI
Cross-platform support in v0.1
Real-time push via service hooks in v0.1

3. High-Level Concept
DevPulse runs two independent polling tracks:

PR track
Fetches pull requests and comment threads → normalizes author identities → classifies events by source and meaning → applies include/exclude inbox rules → collapses grouped events → stores results → raises toast notifications where enabled.

Work item track
Fetches work items for the configured area/iteration → stores them locally → computes days-in-state for aging → feeds the Kanban board window.

A single SQLite database holds all local state. The app never writes back to Azure DevOps.

5.3 Author Identity Normalization
Azure DevOps returns author identities in inconsistent formats across endpoints (display name, email, service account name, renamed account). Before any rule evaluation, DevPulse shall normalize all author references to a canonical identity key.

Normalization shall:
Prefer the uniqueName (email) as the canonical key
Fall back to displayName if uniqueName is absent
Apply user-defined alias mappings from Settings to merge variant forms
Mark identities with EventSource = Bot if the display name or unique name matches a configured bot pattern

Example alias mapping in settings:
"aliases": [
  { "canonical": "john.smith@company.com",
    "variants": ["John Smith", "Smith, John", "jsmith"] }
]

5.6 Needs My Attention — System Inbox
A built-in, non-deletable inbox that sits above all user-defined inboxes and is evaluated first. It catches events that require direct reviewer action.

Default catch conditions:
The current user is listed as a reviewer on the PR
AND one of the following is true:
A human commented after the user’s last action on that PR
A reviewer vote changed to Blocked or Waiting for Author
EventSource = Human AND EventMeaning = Comment AND author is in the configured PO/QA group
Comment text matches any keyword in the configured “needs attention” keyword pack

Notifications for this inbox are always enabled and cannot be disabled. The tray icon badge reflects its unread count.

5.7.2 Rule semantics
All non-empty include conditions in a rule must match (AND logic)
If any exclude condition matches, the rule does not match regardless of includes
An inbox matches if any of its rules match (OR across rules)
Inboxes are evaluated in Order; first matching inbox wins
Needs My Attention is always evaluated first and cannot be reordered
A fallback inbox with no conditions must always exist as the last inbox

5.7.3 Keyword packs
MessageContainsAny and MessageContainsAll accept named keyword packs in addition to inline strings. Packs are defined in Settings and reusable across rules.

Default keyword packs:
Pack name
Keywords
needs-attention
needs test, please review, ready for QA, please verify, ready for test
blocking
changes requested, blocked, waiting for author, do not merge
positive
approved, LGTM, looks good, ship it
hotfix
hotfix, urgent, critical, production issue

5.8 Event Collapsing
When multiple related events arrive in the same poll cycle for the same PR, DevPulse shall group them into a single inbox row rather than N separate rows.

Collapse rules:
Bot comments on the same PR within the same poll cycle collapse into one grouped event
System events on the same PR (auto-complete, reviewer changes, merge) within a 5-minute window collapse into one summary event
Each collapsed group stores a count; the inbox row displays it (e.g., “CodeRabbit added 14 comments on PR #552”)
Expanding a collapsed row shows the individual events underneath
Collapsed groups count as one item for unread count purposes

5.13 Watchers
Watchers are an explicit subscription layer that sits above the inbox rule engine. A watcher causes matching events to always land in a specified inbox (or Needs My Attention) regardless of normal rule order.

Watcher type
Example
Watch author
All events from john.smith@company.com → Prioritized
Watch repository
All events from repo ‘payments-api’ → Prioritized
Watch PR title pattern
PRs whose title matches ‘hotfix*’ → Needs My Attention
Watch work item type
All Feature work items → include on board
Watch work item state
All items entering ‘In Review’ → trigger notification

Watchers are evaluated before inbox rules. A matching watcher short-circuits rule evaluation for that event.

7.2 PR Data Flow
PollingService triggers; guard prevents overlap
AzureDevOpsClient fetches relevant PRs and threads
IdentityNormalizer resolves all authors to canonical identities and EventSource
EventNormalizer produces normalized DevOpsEvent records with EventMeaning
StateStore filters out already-known EventIds
MuteService filters out muted/snoozed PR events
EventCollapser groups remaining events by PR and source within the poll window
RuleEngine evaluates watchers, then Needs My Attention, then user inboxes in order
StateStore persists events with assigned inbox
NotificationService raises toasts for events whose inbox allows it
TrayApplication updates unread counts in tray menu
DebugLogService records trace for each event

7.3 Work Item Data Flow
WorkItemPollingService triggers; guard prevents overlap
WorkItemClient fetches items via WIQL for configured area/iteration
WorkItemNormalizer produces WorkItem records with days-in-state computed from state transition date
WorkItemNormalizer attempts to resolve linked PR IDs from work item relations
StateStore upserts all work items by Id
BoardViewService groups items by column mapping and applies aging thresholds
Board window refreshes if open; stale-data banner cleared

14. Refresh Algorithms
14.1 PR Refresh
Guard: if already running, exit
Fetch relevant PRs from AzureDevOpsClient
For each PR: compare status/votes with pr_snapshots; emit status/vote events if changed
Fetch comment threads; emit comment events for unseen thread/comment IDs
IdentityNormalizer resolves all authors; sets EventSource on each event
EventNormalizer sets EventMeaning on each event
Filter out EventIds already in the store
MuteService removes muted/snoozed events
EventCollapser groups remaining events by PR + source within poll window
RuleEngine: evaluate watchers first, then Needs My Attention, then user inboxes in order
Persist events with InboxName and MatchedRuleDescription
NotificationService raises toasts where inbox.ShowNotifications = true
TrayApplication refreshes unread counts in context menu
DebugLogService records trace for each event
Update last successful PR poll timestamp

14.2 Work Item Refresh
Guard: if already running, exit
Fetch work items via WIQL for configured area/iteration
WorkItemNormalizer: compute DaysInCurrentState from StateChangedAtUtc; set AgingLevel
Attempt to resolve LinkedPullRequestId from work item relations
Upsert all work items in StateStore
BoardViewService groups items by column; applies aging thresholds

16. Error Handling
Application must not crash on network failures, auth failures, malformed config, or partial API failures
Log error, keep tray app running, retry on next scheduled interval
Auth failure: suppress repeated popups, mark status as disconnected, surface quick link to Settings
Work item poll failure: board window shows non-intrusive stale-data banner; cached data remains visible
PR poll failure: inbox views continue to show last cached events
DebugLogService records all exceptions with context

17. Security Requirements
PAT stored via DPAPI or Windows Credential Manager; never in plain text
Logs must never contain the PAT
Settings JSON export must redact the PAT unless explicitly confirmed by the user
Identity alias data is local only; it is not sent to Azure DevOps

18. Performance Requirements
All polling runs asynchronously; UI remains responsive at all times
Overlapping refreshes per track are skipped, not queued
Board window opens immediately from cached local data; no live API call on open
EventCollapser must complete within the poll cycle before notifications fire
SQLite queries for inbox views must return within 100ms under normal load

22. Implementation Notes
Normalize author identities before any rule evaluation. Rules that rely on raw display names will be brittle.
EventSource and EventMeaning are set during normalization and must be treated as immutable after that point.
Keep the rule engine data-driven. There must be no hardcoded author or message checks outside of default seeding.
The “first matching inbox wins” invariant is enforced by RuleEngine. No other component should assign inboxes.
Watchers short-circuit rule evaluation. Document this clearly in code comments to avoid confusion.
The PR and work item polling tracks are fully independent. A failure or hang in one must never affect the other.
The board window must always open instantly from local cache. Never make a live API call on window open.
EventCollapser must run after identity normalization and before RuleEngine. Collapsed events must carry the correct EventSource and EventMeaning of their constituent events.
MuteService must be checked after collapsing and before notification. A muted PR should never produce a toast.
MatchedRuleDescription should be a short human-readable string suitable for display in the debug log, e.g. “EventSourceEquals=Bot”.
The debug window is for diagnostics only. It must never affect polling, rule evaluation, or notification behavior.
